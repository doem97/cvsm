# research-harness v1 设计

> 2026-10-16。取代 2026-10-15 的第三稿。2026-10-17 同步了 T1–T4 开发中做的决定（见 #1、#3、#5 上的 Decision）。

## 0. 是什么

这是一套围绕 git 和 GitHub 的研究开发约定：
- GitHub 原生的 issue、PR、检查和分支保护承载状态机；
- agent 通过 AGENTS.md 和 skill 知道怎么推进；
- 一个 guard 检查兜住 skill 保证不了的事。

另外几点：
- **没有要安装的程序**。不自造概念，不存任何状态。
- **分工**：skill 管怎么做，检查管不能错。能机械检查的规则放进 guard；查不了的在 AGENTS.md 里写一行，由审查把关；需要人合并的改动，人在合并时再看一遍。
- **不管的事**：研究方法（seed 数、实验设计、何时重跑）、分析与可视化，以及 agent 在任务内部怎么实现。
- **只做核心，环境由项目适配**：harness 提供流程、接口和一个本机参考实现。各项目 clone 后，由自己的 agent 开 issue，适配自己的代码库、开发机和集群（SLURM、rjob、rlaunch 等）；harness 不预置环境适配器，也不预设存储或后端。
- **使用方式**：人在 Codex 交互会话里用短句推进，会话是 full permission，不依赖沙箱。可以同时开几个会话，各承担一个角色。

## 1. 原则

1. **Less is more**：只约束六类东西：接口、文件、状态机、代码约定、Git 用法、context。每条规则都要对应一种主要的失败。
2. **状态在 GitHub 上**：仓库里没有状态、计划或进度文件。
3. **会话不是状态**：会话随时可以丢；凡是改变状态的事，都立刻写回 GitHub 或 git。
4. **机制不是策略**：工具只记录事实、展示差异；能不能比、要不要重跑，由人判断。
5. **关口少而固定**：没有卡点就一直推进，遇到关口或卡点才停。
6. **合并分级**：默认由人合并；任务标为 `Merge: agent` 时，由 agent 通过 `.github/scripts/merge.py` 合并。碰了受保护路径的 PR 一律由人合并。
7. **按高智能模式设计**：假定 agent 是能遵守写清楚的规则的高能力模型；脚本固化流程，不防御格式错乱、冒充或外人。
8. **人只在会话里做决定**：GitHub 上的操作都由 agent 执行并记录。

## 2. 六类约束

| 约束 | 定什么 | 怎么保证 |
|---|---|---|
| 状态机 | 状态只用 GitHub 原生字段表达，另加 1 个 label（§3） | GitHub 自己维护；默认人合并，`Merge: agent` 的任务由 agent 通过 merge.py 合并 |
| 接口 | 交接只走固定格式：3 种 issue 表单、PR 模板、审查评论、决定记录、卡点评论、结果评论、运行记录（§4） | 表单和模板定格式；guard 检查 PR 格式 |
| 文件 | 一个项目一个仓库，目录有白名单；`.md` 只能放在固定位置；不许出现计划、进度、笔记类文件（§5） | guard |
| 代码约定 | 共享代码和方法模块分开；每个任务在 issue 里声明改动范围（§5） | guard 检查改动不超出范围 |
| Git 用法 | 1 个任务 = 1 个 issue = 1 个分支 = 1 个 worktree = 1 个 PR；命名和标题格式固定；只用 squash 合并（§6） | 分支保护；guard |
| context | 每个角色读什么、写什么；先读状态再动手（§7） | AGENTS.md 和 skill；guard 保护规则文件 |

## 3. 状态机

### 3.1 状态

| 对象 | 状态 | 在 GitHub 上怎么看 | 谁推动 |
|---|---|---|---|
| 研究（父 issue，label `study`） | 进行中 | 开着，还有没关的子 issue | 发布时创建 |
| | 待分析 | 开着，子 issue 全部关闭 | 自动 |
| | 结束 | 关成 completed（附结论），或 not planned | 人决定，agent 执行 |
| 任务（子 issue，label `code` 或 `run`） | 等依赖 | 原生 Blocked 标记（blocked-by 的 issue 还没关） | 自动 |
| | 就绪 | 开着，没被挡住，也没有关联分支 | 自动 |
| | 进行中 | 有关联分支（用 `gh issue develop` 建） | 认领时 |
| | 等你决定 | label `needs-decision`，加一条卡点评论 | agent 加上；人答复后去掉 |
| | 审查中 | PR 已打开，检查或审查还没完成 | agent |
| | 待合并 | 检查全绿，最新的审查结论是针对当前 head 提交的 pass | agent |
| | 完成 | 代码任务的 PR 合并后 issue 自动关闭；运行任务贴出结果后关闭 | 人决定后 agent 用 merge.py --human 合并；Merge: agent 的任务由 agent 用 merge.py 合并；运行任务由 agent 关闭 |
| | 放弃 | 关成 not planned | 人决定，agent 执行 |

开发仓库（包括 research-harness 自己）用同一张表：父 issue 换成计划（label `plan`），没有运行任务。

### 3.2 关口：一切顺利也要停
1. 新增或改变已批准的工作：发布计划；改任务的目标、范围、验收或合并方式（Merge）；改受保护路径。
2. 合并，除非任务标为 `Merge: agent`。这时 agent 在待合并后用 `python .github/scripts/merge.py <PR>` 合并；merge.py 拒绝碰了受保护路径的 PR，也拒绝当前 head 没审查通过的 PR。其他情况，或 merge.py 拒绝时，待合并的 PR 本身就是请求，不打 `needs-decision`，也不贴卡点评论。人在会话里明确说合并时，agent 用 `python .github/scripts/merge.py <PR> --human` 合并。
3. 超出预算：token、时间或 GPU 小时。
4. 研究下结论并关闭。

人明确下的指令本身就算批准。比如说了"提个 issue：X"，agent 不必再问一遍。

### 3.3 卡点
- **停下问人**：要过关口；同一个失败连续出现 3 次；审查连续 3 次给出 changes；目标有歧义，并且会影响交付物。
- **自己处理**：测试或 CI 失败、合并冲突、infra 失败重试、范围内的 bug，以及结论为 changes 的审查：修掉它指出的问题，再请新的审查看新的 head。结论为 pass 时循环结束；随 pass 附带的 minor 意见，范围内的当场修掉，再请一次新的审查；剩下的由实现者在 PR 上贴一条评论，逐条提处理办法（开新 issue、并进已有 issue、不处理），各附一行理由。人说合并即批准这些提议，由执行合并的 agent 照办。
- **范围外的 bug**：建一个 issue，当前工作照常继续，不塞进当前 PR。

同一个卡点只问一次，带上证据、最多 3 个选项和推荐。人在场时在会话里问。不在场时打上 `needs-decision`、贴卡点评论，然后转去做别的就绪任务。

### 3.4 指令与汇报
- 每条指令就是一个目标状态。例如："做 #12"是推进到待合并（`Merge: agent` 的任务推进到合并完成）；"把 #10 推到待分析"；"继续"是推进到下一个关口。agent 只在到达目标、碰到关口或遇到卡点时停下。
- 每次停下只汇报三行，带链接：完成了什么、等你做什么、接下来做什么。

## 4. 接口

给 agent 的指令（AGENTS.md、skill）、代码、PR 标题和格式关键字（`Closes`、`Decision:`、`Blocked:` 等）用英文：LLM 对英文原生适配，指令更准确。面向人的接口用 AGENTS.md 的 Project 一节设定的语言，本仓库是中文：PR 正文、issue 和 PR 评论、汇报、表单说明、README、结果评论；审查评论除外，Verdict 行下面保留审查工具的原文；docs/ 由人写，也用中文。各接口的字段如下：

| 接口 | 字段 / 格式 |
|---|---|
| 研究表单 `study.yml` | Question；Comparison（各组只写配置差异）；Criteria；Budget；Context（链接） |
| 代码任务表单 `code.yml` | Goal（≤ 3 句）；Scope（路径 glob，每行一个）；Acceptance（命令，每行一个）；Budget；Merge（human 或 agent，默认 human） |
| 运行任务表单 `run.yml` | Runs（每行一条命令，含配置覆盖和 seed）；Budget（GPU 小时）；Report（指标名，空格分隔） |
| 父子关系与依赖 | 发布时用 `gh issue create --parent N --blocked-by M` 设置，不写进正文 |
| PR 模板 | 第一行 `Closes #N`；Changes（≤ 5 条）；Acceptance（命令和结果）；Out of scope（新建的 issue，没有就写 none） |
| 决定记录（issue 评论） | `Decision: <选项> — <一行理由>` |
| 卡点评论 | `Blocked:` 一行；`Evidence:` 链接；`Options:` ≤ 3 个；`Recommend:` |
| 审查评论（PR 评论） | 第一行 `Verdict: pass @ <head SHA>` 或 `Verdict: changes @ <head SHA>`，审查写完整 SHA，merge.py 认至少 7 位的前缀；只有阻断问题才给 changes。下面原样贴审查工具自己的意见（Codex 或 Claude 的原生输出，可以是英文，不翻译不改写），不阻断的标为 minor。由审查会话自己贴；用 Codex 内置的 `codex exec review` 时，由运行它的会话原样转贴，结论按它自己的优先级对应：有 `[P0]` 或 `[P1]` 的问题记 changes，否则记 pass。merge.py 只读 PR 评论，取最新一条第一行以 `Verdict:` 开头的，要求是 `Verdict: pass @ <SHA>`，且 SHA 是当前 head 的前缀 |
| 结果评论 | 由结果脚本生成的表：按除 seed 外的配置分组，给出 n、均值、标准差和失败数；组间 commit、环境或数据不同就标出来，并附 `git diff --stat`；没有指标、未完成和被删除的 run 也列出来 |
| 运行记录（MLflow run） | `rh.*` 参数（MLflow 的参数写入后不能改）：issue、命令、seed、机器、commit、工作区是否干净、环境锁和数据清单的哈希、GPU、退出码；工作区的 diff、未跟踪文件清单和运行日志作为产物；训练代码用 MLflow 的标准 API 记指标（`MLFLOW_RUN_ID` 让它接到同一个 run），或者写 `metrics.json` |

运行记录写进 `MLFLOW_TRACKING_URI` 指定的 MLflow 后端；不设时用主 clone 根目录下的 `mlflow.db`，产物放在旁边的 `mlartifacts/`，不随当前目录漂移。harness 不预设任何服务或集群后端。记录不改不删，也不运行 `mlflow gc`。MLflow 的网页可以用来浏览记录，但不是必需的。

## 5. 文件与代码约定

项目模板的目录如下。白名单写在 `guard.toml` 里，项目可以改：

```
AGENTS.md            规则，人写，≤ 80 行
.agents/skills/      plan、implement、review、run；.claude/skills 软链到这里
.codex/rules/        harness.rules：禁止直接运行 gh pr merge
.claude/             settings.json：同样禁止直接运行 gh pr merge
.github/             issue 表单、PR 模板、guard.toml、scripts（guard.py、merge.py）、workflows（guard、test）
src/<pkg>/core/      共享代码
src/<pkg>/methods/   每个方法一个模块，用配置选择
configs/  scripts/  tests/  docs/  README.md
```

- **`.md` 的位置**：只允许 README.md、AGENTS.md，以及 docs/、.agents/skills/、.github/ 这几个目录。任何位置都不许出现 TODO、NOTES、PLAN、PROGRESS 这类文件。
- **只认 AGENTS.md**：不接受 CLAUDE.md，guard 会拒收。项目没有 CLAUDE.md 时，Claude Code 默认读 AGENTS.md。
- **受保护路径**：AGENTS.md、.agents/、.codex/、.claude/、.github/，以及项目声明的评测和数据路径。只有任务的 Scope 里明确列出，才能改。
- **代码约定**：方法任务只改自己的模块、配置和测试；改共享代码要单独开一个任务；docs/ 由人写。

## 6. Git 用法

**main 的规则**
- 只能通过 PR 改动，必须通过 `guard` 和 `test` 两个检查，禁止强推。
- 只允许 squash 合并，合并后自动删除分支。
- 不要求批准：只有一个账号。人在会话里说合并，agent 用 `python .github/scripts/merge.py <PR> --human` 合并，这就是批准；`Merge: agent` 的任务由 merge.py 按规则合并。

**一个任务**
- 分支 `t/<N>-<slug>`，worktree 放在 `../worktrees/<N>-<slug>`（相对主 clone）。
- PR 标题格式是 `<type>(#N): <summary>`，type 取 feat、fix、refactor、test、exp、docs、chore 之一。
- squash 之后，main 上的每条 commit 对应一个 issue。

**agent 不能做的**
- 不直接运行 `gh pr merge`。只有 `Merge: agent` 的任务，才由 agent 用 `python .github/scripts/merge.py <PR>` 合并：它检查 issue 的 Merge 字段是 agent、改动（含重命名前后的路径）不碰 PR 目标分支上 guard.toml 列出的受保护路径、最新一条 `Verdict:` 评论是当前 head 的 pass；都满足才用 `gh pr merge --squash --match-head-commit <SHA>` 合并，否则拒绝，等人合并。
- 人在会话里明确说合并某个 PR 时，agent 用 `python .github/scripts/merge.py <PR> --human` 合并当前 head：同样的 squash 命令，跳过上面三项检查，因为人已经决定。
- 不往 main 推，不动别人的分支。tag 只由人打。
- `.codex/rules/harness.rules` 里只有一条规则：`gh pr merge` 设为 forbidden。Codex 在选择沙箱之前就按规则拒绝命令，所以 full permission 下这条规则同样生效（见源码 `core/src/exec_policy.rs`；S0 实测）。Claude Code 用 `.claude/settings.json` 里的 `permissions.deny` 做同一件事。

## 7. context

| 角色（skill） | 读 | 写 | 停在 |
|---|---|---|---|
| plan | 代码、以往的研究和结果评论、运行记录 | 发布时建的研究和任务 issue | 发布（关口） |
| implement | AGENTS.md、自己的 issue、父 issue 上的决定、范围内的代码，以及它用到的接口 | 范围内的文件、PR、卡点评论 | 待合并；`Merge: agent` 的任务做到合并完成 |
| review | PR 及其 diff、它关闭的 issue 及评论、父 issue 上的决定 | 一条审查评论：Verdict 行加审查工具的原文 | 给出结论 |
| run | 运行 issue、它所属的研究 issue 及其决定、运行记录 | 运行记录、结果评论 | 运行结束 |

- 每条指令开始时先读状态：开着的研究及其子 issue、打开的 PR 及其检查、带 `needs-decision` 的 issue。
- 认领任务就是用 `gh issue develop` 建关联分支；认领后再查一次，如果还有别的分支也关联上了，删掉自己的，转去做别的。已经有关联分支的任务，只有指令点名或本会话自己认领的才接着做，所以开几个会话并行是安全的。
- 质量主要靠实现者开 PR 前的自我迭代：跑 Acceptance，派新的 subagent 或会话对照 issue 审 diff，迭代到 Acceptance 通过、没有阻断问题为止。
- 审查是最后一道独立检查：另开一个新会话（Claude Code 的新 subagent，或新的 `codex exec` 会话，或 Codex 内置的 `codex exec review`），按 review skill 做。它只拿到 PR 编号，自己去读 PR、diff、对应的 issue 和父 issue 上的决定，不看实现者的会话或总结，以免带入实现者的偏见。审查清单按高智能模式：合同、真实输入和出错路径上的正确性、与 AGENTS.md 和 spec 及代码的一致性、锁定合同的测试、简洁；不要求防御格式错乱、伪造、外人或恶意输入，除非 issue 要求。
- 审查给出 pass 后，范围内的 minor 意见当场修掉，再请一次新的审查；剩下的 minor 在 PR 上逐条提处理办法，人说合并即批准，由执行合并的 agent 照办（同 §3.3）。
- agent 不写记忆、笔记或文档。讨论内容不留存，只有决定和结论写到 GitHub 上。

## 8. guard

用 `pull_request_target` 触发，代码取自 main，从不执行 PR 里的代码。按顺序检查：
1. PR 正文恰好链接一个任务 issue（`Closes #N`）。
2. 改动的文件都在目录白名单内；`.md` 的位置和禁用文件名都合规。
3. 改动不超出 issue 的 Scope；受保护路径只有在 Scope 里列出时才允许改。
4. PR 标题格式正确；模板各节齐全；长度在上限内（上限在 `guard.toml` 里设，默认 PR 正文 ≤ 40 行）。
5. （可选）diff 行数上限。

`test` 跑项目自己的测试，用 `pull_request` 触发。

## 10. 起步（S0）与验收

**S0（已完成）**
1. 建仓库 `doem97/research-harness`。
2. 第一个 PR（#8）包含本设计文档、guard、PR 模板、issue 表单和 guard.toml。合并后把 `guard` 和 `test` 设为必过检查。
3. 实测结果：
   - 私有仓库设分支保护需要 Pro，已开通；
   - 项目级 `.codex/rules` 生效：`codex execpolicy check` 对 `gh pr merge` 给出 forbidden；
   - 长时间运行的任务怎么挂到后台、之后怎么回来查，留到试点验证。

**试点**：在本机做一个 toy CIFAR 项目，约 1–2 GPU 小时。下面全部通过，v1 就算完成：
1. 从讨论到发布：建 1 个研究、2 个代码任务、1 个运行任务，带依赖。
2. 把一个代码任务做到待合并，人合并后 issue 自动关闭。
3. guard 能拒收三种情况：范围外的改动、多余的 `.md`、没列进 Scope 却改了 AGENTS.md。
4. 卡点：一个需要扩大范围的任务，在会话里问人，决定记到 issue 上。
5. 运行：跑基线和变体；两次运行之间改一处共享代码，结果表能标出差异并附 diff。
6. 中途关掉会话，新会话说"继续 #N"能接上；两个会话不会认领同一个任务。
