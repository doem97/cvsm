All of CVSM's workflow state lives in GitHub: issues, sub-issues, dependencies, linked branches, PRs, checks and closed states. The repo holds no plan, progress or notes files, and a session holds nothing, so any session can end at any moment and the next one reads where things stand.

<Loop lang="en" />

## Parents and sub-issues

A parent issue holds the why; its sub-issues hold the work.

- **`study`**: a research question. Its body is the [study form](/cvsm/reference/issue-forms/), including the spec.
- **`plan`**: development work, with `### Goal` and `### Context`.
- **`code`**: one change inside a fixed Scope, done in one branch and one PR.
- **`run`**: a set of runs, closed with a results comment. A run task has no PR.

The only other label is `needs-decision`. Parents and dependencies are native GitHub fields, set when the issue is created and never written into the body:

```sh
gh issue create --label run --title "<title>" --parent 10 --blocked-by 11 --body "..."
```

For example, study #10 has code task #11 and run task #12, and #12 is blocked by #11 because its runs need the merged code.

## Task states

Every state below is something GitHub already shows.

| State | How GitHub shows it |
|---|---|
| Waiting | Blocked by an issue that is still open |
| Ready | Open, not blocked, no linked branch |
| In progress | Has a linked branch |
| Needs decision | Label `needs-decision` plus a blocker comment |
| In review | PR open, checks or review not finished |
| Merge-ready | `guard` and `test` green, and the latest review is `Verdict: pass @ <head SHA>` for the current head |
| Done | A `code` issue closes when its PR merges (`Closes #N`); a `run` issue is closed by the agent with its results comment |
| Abandoned | Closed as not planned, on the human's explicit instruction |

## Parent states

| State | How GitHub shows it |
|---|---|
| In progress | Open, with open sub-issues |
| Awaits analysis | Open, all sub-issues closed |
| Closed | Completed with the conclusion, or not planned, on the human's explicit instruction |

Concluding a study is [gate 04](/cvsm/concepts/gates-and-blockers/).

## Reading state

Every instruction starts by reading state from GitHub, never from chat memory: open `study` and `plan` issues with their sub-issue summaries, open PRs with their checks, and issues labelled `needs-decision`.

## Claiming a task

A session claims a ready issue by creating a linked branch, then checks that no other branch got linked at the same time:

```sh
gh issue develop 11 --name t/11-<slug> --base main
gh issue develop --list 11
```

If another branch is linked too, the session deletes its own and picks other work. A session continues an in-progress issue only if the instruction names it or the session claimed it itself. That is what makes parallel sessions safe.

## One task, one of everything

One task is one issue, one branch `t/<N>-<slug>`, one worktree `../worktrees/<N>-<slug>` beside the main clone, and one PR. After the squash merge, each commit on `main` maps to one issue.

<Aside type="tip">
Because state is on GitHub, you can always ask a fresh session "what's waiting for me?" and get the same answer as from the session that did the work.
</Aside>
